## 2. 課題の詳細

### A. 品質（応答の正しさ）

#### A-1. 単位異常検知が商品マスタを参照せず、汚染された学習データだけで発火【最重要】

- `src/plugins/exception_plugin.py:100`（`detect_unit_anomaly`）は顧客プロファイルの
  `typical_unit` と注文単位の不一致だけで `is_anomaly=True` を返す。
  - **商品マスタの標準単位と照合していない**（りんご P-001 の標準単位は「箱」なのに、
    プロファイルに `typical_unit=kg` が入っているため「りんご5箱」が毎回異常扱い）。
  - 数量異常（`detect_quantity_anomaly`）にある「3件未満はスキップ」の**最低データ件数の閾値がない**。
- プロファイル汚染の経路: QC を本番 Container Apps に対して実行 → 受注確定ごとに
  `_run_learning`（`orchestrator.py:2683`）が `record_pattern` / `update_customer_profile` を実行
  → **QC テスト入力そのものが「顧客の通常パターン」として学習される**フィードバックループ。
- 影響: 78メッセージ中16件（20%）で不要な確認質問。さらに確認待ち状態
  （`pending_exists=true`）を作るため、後続メッセージの誤ルーティング（A-2）と
  在庫チェックのスキップ（ケース50）に連鎖する。**NG 11件中 6件以上の根本原因**。

#### A-2. 「変更対象の現在注文が見当たりません」デッドエンド

- `orchestrator.py:704` — `if not current_order and _looks_like_change_only_message(message)` が
  テンプレート応答を返して処理を打ち切る。
- `_looks_like_change_only_message`（`orchestrator.py:3684`）は「追加」「変更」「やっぱり」等の
  **単純キーワード一致**であり:
  - 「やっぱりみかん20個お願い」（キャンセル後の再注文）→ 商品・数量が明示されているのに新規注文にフォールバックしない（ケース16/33）。
  - `pending_order_draft`（確認待ちドラフト）が存在しても current_order しか見ないため、
    確認待ち中の「バナナだけ20kgに変更」「あとバナナも5kg追加で」が全滅（ケース17/34/49）。
- `IntentUnderstandingService`（ルール+LLM の意図分類）と、この orchestrator 内の
  別系統キーワード判定（`_looks_like_change_only_message` / `_resolve_line_action_type` 等）が
  **二重実装**になっており、判定が食い違う。

#### A-3. 複数商品・複数配送日の取りこぼし

- 確認質問が先頭商品のみに言及し、他の商品に触れない（ケース22/39: バナナ脱落、
  ケース51: みかん脱落）。確認テンプレート/プロンプトに「全商品を列挙する」制約がない。
- 注文ドラフトは `delivery_date` 単一のため「明日にりんご、明後日にバナナ」を表現できない
  （モデル上の制約。ケース22/39）。

#### A-4. 数量異常検知の過剰発火

- `exception_plugin.py:61` — `std_dev == 0` のとき `ordered_qty != avg_qty` なら**乖離幅に関係なく**異常。
  過去3回同じ数量だっただけで、次に数量を変えると必ず確認質問になる（ケース51）。

### B. 性能（レイテンシ・コスト）

#### B-1. 直列 LLM 呼び出しが多すぎる

1メッセージの標準経路: 意図分類（ルール外れ時 LLM）→ Intake Agent（ツール呼び出し込み、平均5.4s）
→ Exception Agent（平均4.5s）→ 最終応答生成 LLM。合計 **10〜20s**。
LINE の replyToken 失効（30s）に対する余裕が薄く、体感品質も悪い。

#### B-2. Exception Agent は LLM である必要がない

`detect_quantity_anomaly` / `detect_unit_anomaly` は**決定的な計算**であり、Exception Agent は
それを呼んで JSON に写すだけの LLM ラッパー（1メッセージあたり約4.5sの純粋なオーバーヘッド）。
既に同等のコード実装（`src/services/anomaly_rules.py` の `classify_quantity_anomaly`、
`orchestrator.py:3783` の `_evaluate_anomaly_severity`）が存在しており、二重実装にもなっている。

#### B-3. 意図分類の LLM fallback が空振りする

QC ログでは「アボカド5個、マンゴー3個お願いします」のような明白な新規注文でも
`intent=unclear, confidence=0.0` になっている。ルールが `new_order` を積極判定しないため、
LLM 呼び出し1回分のレイテンシを払った上で結局 UNCLEAR でチェーンに流れている。

#### B-4. 生成した LLM 応答をテンプレートで捨てている

LINE の主要経路の多くが「経路: テンプレート上書き」= Orchestrator Agent で最終応答を
LLM 生成した後、テンプレートで上書き。**上書きが確定しているケースでは最終応答 LLM 呼び出し自体が不要**。

#### B-5. Agent・ナレッジをメッセージごとに再構築

`_make_*_agent` が毎回 Kernel/Plugin/ChatCompletionAgent を生成し、`definitions.py` の
`_load_knowledge` が毎回ディスクからナレッジを読む（キャッシュなし）。LLM に比べれば軽微だが無駄。

### C. 保守性・テスト基盤

#### C-1. orchestrator.py が 4,064 行のモノリス

意図ルーティング・業務ロジック・在庫判定・テンプレート描画・メール整形・正規化ヘルパが
1ファイルに混在。ルール分岐が積み木状に増えており、A-2 のようなデッドエンドが生まれやすい。

#### C-2. QC の再現性・自動化不足

- QC は本番環境に対する実行で、**ケース間で在庫・学習プロファイル・セッション状態が汚染**される
  （ケース26/43 の「在庫ちょうど」が在庫0で開始し誤NG。学習汚染は A-1 の根因）。
- 判定は AI 判定のみ（人判定列は全て `-`）で、回帰が CI に乗っていない。

#### C-3. プロンプトの肥大化

`definitions.py` の Intake instructions は「〜してはいけない」の否定形指示の積み重ねで
制御しており、ケースが増えるたびに追記される構造。プロンプトだけで分岐を制御する限界に来ている。

## 3. 改善計画

### Phase 1: 品質の即効修正（見込み: NG 11件中 9件解消、確認質問ノイズ20%→ほぼ0）

| # | 対応 | 対象 | 内容 |
|---|---|---|---|
| 1-1 | 単位異常検知をマスタ基準に | `exception_plugin.py` | `detect_unit_anomaly` で **商品マスタの標準単位と一致するなら異常としない**。プロファイル `typical_unit` は「マスタとも注文とも違う」場合の補助情報に格下げ。数量異常と同様に `total_orders >= 3` の閾値を追加 |
| 1-2 | 数量異常の std_dev=0 緩和 | `exception_plugin.py` | `std_dev == 0` 時は「avg の N 倍以上（例: 3倍）または 1/N 以下」のときのみ異常。`ordered != avg` 即異常をやめる |
| 1-3 | デッドエンドの解消 | `orchestrator.py:704` 付近 | 変更系キーワード検出時のフォールバック順を「①pending_order_draft があればドラフト更新として Intake（ドラフト反映モード）へ ②商品名+数量が読み取れれば新規注文として処理 ③どちらも不可のときのみ『変更対象なし』テンプレート」に変更 |
| 1-4 | 確認質問で全商品列挙 | `definitions.py` / テンプレート | Intake/最終応答の指示に「確認質問でも注文内の**全商品を必ず列挙**する」を追加し、QC チェックにも追加 |
| 1-5 | 学習のQC汚染防止 | `learning_service.py` / QC | QC 用顧客（または `session_id` prefix `qc-`）を学習対象から除外。加えて `scripts/line_qc/run.py` の前処理で対象顧客のプロファイル/パターンをリセット |
| 1-6 | QC の在庫分離 | `scripts/line_qc/run.py` | 在庫依存ケース（境界値・欠品）の直前に該当商品の在庫をケース定義値へセットする per-case リセットを追加 |

検証: `python scripts/add_stock/run.py` → `python scripts/line_qc/run.py --verbose` を再実行し、
§4.44 として記録。目標 **55/57 以上**（複数配送日ケースは Phase 3 まで既知制約として明記）。

### Phase 2: レイテンシ削減（見込み: 平均応答 10〜15s → 5〜8s）

| # | 対応 | 内容 |
|---|---|---|
| 2-1 | Exception Agent の LLM 撤去 | 異常検知を `anomaly_rules` / `_evaluate_anomaly_severity` へ一本化し、Intake 直後にコードで直接実行（**約4.5s/メッセージ削減**、実装の二重化も解消） |
| 2-2 | テンプレート確定経路の最終 LLM スキップ | 「テンプレート上書き」になることが確定している分岐（受注確定・キャンセル確認・在庫不足通知等）では `_generate_final_response` を呼ばない |
| 2-3 | 意図分類ルールの拡充 | 「商品名+数量+依頼表現」は rule で `new_order` 即決にし、LLM fallback を本当に曖昧な文だけに限定 |
| 2-4 | Agent/ナレッジのキャッシュ | チャネル別 instructions とナレッジ読込を `functools.lru_cache` 等でキャッシュ。Agent インスタンスもチャネル単位で再利用 |
| 2-5 | 計測の常設化 | メッセージ全体の end-to-end 時間と LLM 呼び出し回数を debug_log とアプリログに常時記録し、QC ログ集計スクリプトで平均/最大を出す |

### Phase 3: 構造改善（中期・回帰防止）

| # | 対応 | 内容 |
|---|---|---|
| 3-1 | 意図判定の一元化 | orchestrator 内の `_looks_like_change_only_message` / `_resolve_line_action_type` 等のキーワード判定を廃止し、`IntentUnderstandingService` に統合。判定結果（intent + 対象=pending/current/new）を単一の enum で表現 |
| 3-2 | orchestrator の分割 | ①ルーティング（intent → ハンドラ）②業務サービス（既存の `order_application` 等へ寄せる）③応答レンダリング（テンプレート/LLM）の3層に分離。目安: 1ファイル1,000行以下 |
| 3-3 | 複数配送日対応 | 注文ドラフトを配送日ごとに分割生成できるようにし、「明日にA、明後日にB」を2受注として処理（ケース22/39 の恒久対応） |
| 3-4 | QC の CI 化 | LINE Tester API 経由の QC をテスト用テナント/顧客に対して実行できるようにし、主要20ケース程度のスモークを PR CI（または nightly）に組み込む。AI 判定に加えて機械チェック（order_saved・在庫通知有無・全商品言及）を正とする |
| 3-5 | プロンプトの整理 | Phase 1〜3 でコード側に移した判定（単位確認・needs_confirmation 基準）を instructions から削除し、プロンプトは「抽出と表現」に専念させる |

### 進め方

1. Phase 1 は 1-1〜1-6 を1つの PR 群として最優先で実施（各修正は独立しており小さい）。
2. Phase 1 完了後に QC を再実行してベースラインを更新し、その数値を Phase 2 の効果測定の基準にする。
3. Phase 2 の 2-1/2-2 は応答品質に影響し得るため、QC 全ケース + `pytest` の回帰確認をセットで行う。
4. Phase 3 はハッカソン審査期間（デプロイ維持）と衝突しないよう、審査影響の小さい 3-1→3-4→3-2 の順で段階投入する。
